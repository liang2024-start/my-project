# Proposal

## Why

星禾数智正处于招聘高峰期，当前招聘全链路靠人工与线下沟通：JD 靠口头传递、简历靠人工逐份看、推荐与部门反馈靠微信/口头催办，导致筛选标准不统一、推荐无依据可查、等待时长不可见。客户明确提出"用 AI 提效"，但同时划定了合规红线：**AI 只能辅助初筛，绝不能自动淘汰候选人，也不能替专员提交推荐**。

本变更以已评审的 PRD（V1.0）与可点击原型为输入，把"确认条件 → 解析简历 → 人工核对 → 人工推荐 → 部门反馈 → 结果回录"这条业务链固化为可开发、可验收的规格，确保实现阶段不因口径模糊而放大合规风险。

## What Changes

- 新增岗位需求承接能力：需求发布/录入、条件与权重确认版本、澄清问询留痕、变更重筛、挂起与需求结束确认。
- 新增简历解析与人工核对能力：意向确认前置、逐份上传解析、逐项对照与原文证据、ABC 分级/评分、"信息不足"标记、待核实问题、版本与查重、同人多岗关联。
- 新增推荐与部门反馈能力：AI 生成的推荐草稿可由专员编辑、**必须人工提交**、"待部门决定"状态可见、部门三选一反馈（拒绝必填原因）、反馈通知推送至推荐人。
- 新增结果回录与用人结果反馈：面试/Offer/实际入职回录（不做飞书对接、不做 Offer 流程）、部门经理与面试官在入职观察期后回评用人结果并通知推荐人、双轨验证数据留存。
- 新增账号、角色与权限体系：账号即登录凭证（停用不可登录）、五类角色能力矩阵、岗位维度数据隔离、职责分离、越权拦截留痕。
- 新增平台管理与看板：用户创建与角色分配、平台配置（自动淘汰能力在产品层永久关闭）、审计日志、满足率/时效/卡点看板。

## Capabilities

### New Capabilities
- `job-requisition`: 招聘需求发布与录入、条件与权重确认版本、澄清问询留痕、需求变更、挂起与需求结束确认。
- `resume-screening`: 面试意向确认前置、PDF 简历上传与解析、逐项对照与原文证据、评分/分级、信息不足标记、待核实问题、版本与查重、同人多岗关联。
- `recommendation-workflow`: 推荐材料草稿、人工提交与撤回、推荐状态与"待部门决定"可见性、低分仍可推荐但须说明差距。
- `department-feedback`: 用人部门反馈工作台三选一（要面试/不要面试/需补充）、拒绝原因必填、反馈通知送达推荐人、等待时长与卡点预警。
- `hiring-outcome`: 面试/Offer/入职结果回录、用人结果反馈（部门经理与面试官）、双轨验证数据、需求结束确认。
- `access-control`: 账号登录与状态、五类角色能力矩阵、岗位维度隔离、同岗协作可见性、职责分离与越权留痕。
- `platform-administration`: 平台用户创建与角色分配、停用/启用/重置密码、平台配置与合规开关锁定、只读审计日志。
- `recruitment-analytics`: 招聘看板指标（满足率/转化/时效）、卡点预警与催办、口径未确认时的降级展示。

### Modified Capabilities
（无：本项目为从零搭建，尚无既有 specs。）

## Impact

- 受影响系统：Web 端的岗位需求工作台、简历筛选与核对工作台、部门反馈工作台、数据看板、平台管理；小程序端范围待 C13 确认。
- 数据模型：新增需求/条件版本/澄清记录/简历文件/应聘记录/解析结果/推荐/部门反馈/面试与 Offer 回录/入职与用人结果/账号与角色/审计日志/通知等实体。
- 外部依赖：PDF 解析与 LLM 解析服务（需可追溯证据输出）、短信/邮件通知；飞书仅人工使用，**不做系统对接**（C12 待确认轻量联动）。
- 合规约束：任何实现不得提供自动淘汰能力（一票否决 V7）；专员跨岗位材料不可见（一票否决 V8）。
- 待确认事项：C1–C16 在规格中以 TBD 标注，配置化实现，确认前不得固定为业务规则（涉及推送口径、评分形态、淘汰线、3 个工作日口径、推送比例、报表口径、权限边界、版本口径、双端差异、挂起规则、历史迁移、隐私留存）。
