# Spec Delta

## Purpose

把"是否面试"的决定权完整交给用人部门，并让每次决定都带上原因与后续要求、自动回流给推荐人，避免推荐石沉大海或拒绝无据可查。

## ADDED Requirements

### Requirement: 用人部门对每条推荐做三选一反馈

用人部门 MUST 在反馈工作台对每条"已推荐-待部门决定"的推荐做出选择：同意面试、拒绝面试、需要补充信息。该决定 MUST 仅由用人部门经理操作，用人部门面试官、招聘专员、招聘经理与平台管理员 MUST NOT 代为决定。

#### Scenario: 部门经理同意面试

- **WHEN** 部门经理选择"同意面试"
- **THEN** 系统要求填写面试反馈或安排说明（轮次、考察重点、期望时间等）后提交，状态变为"已反馈-待面试"

#### Scenario: 面试官尝试做决定

- **WHEN** 用人部门面试官打开同一推荐
- **THEN** 页面展示推荐材料但不显示决定按钮，并提示面试决定由部门经理做出

#### Scenario: 专员尝试代为决定

- **WHEN** 招聘专员调用面试决定接口
- **THEN** 系统拒绝并提示权限不足，推荐状态不变

### Requirement: 拒绝面试必须填写原因

当用人部门选择"拒绝面试"时，拒绝原因 MUST 为必填项；原因为空或仅含空白字符时系统 MUST 拒绝提交。反馈 MUST 记录反馈人、反馈时间与原因。

#### Scenario: 未填原因即提交

- **WHEN** 部门经理点击提交但拒绝原因为空
- **THEN** 系统拒绝提交并提示"拒绝原因必填"，推荐状态保持"待部门决定"

#### Scenario: 填写原因后提交

- **WHEN** 部门经理填写具体原因（如"项目经验与数据建模方向不符"）并提交
- **THEN** 推荐状态变为"已拒绝"，原因写入反馈记录并同步给推荐专员

### Requirement: 需要补充信息必须给出补充要求

当用人部门选择"需要补充信息"时，系统 MUST 要求填写具体补充要求；提交后推荐状态 MUST 变为"待补充"，并在专员补充材料后允许重新进入核对与推荐流转。

#### Scenario: 提交补充要求

- **WHEN** 部门经理填写"请补充数据建模相关项目材料"并提交
- **THEN** 状态变为"待补充"，系统通知推荐专员，并展示补充要求原文

#### Scenario: 专员补充材料后

- **WHEN** 专员补充材料并重新提交
- **THEN** 推荐回到核对流程，原补充要求与反馈记录保留可查

### Requirement: 反馈结果自动通知推荐人

每次部门反馈提交后，系统 SHALL 生成通知推送至该候选人的推荐专员（并抄送招聘经理），通知 MUST 包含候选人、反馈类型、反馈人与摘要，并提供跳转到对应推荐记录的入口。通知 MUST 支持未读计数与已读标记。

#### Scenario: 部门同意后面试通知专员

- **WHEN** 部门经理提交"同意面试"及面试安排
- **THEN** 推荐专员的通知入口出现未读红点，点开后定位到该候选人的反馈详情

#### Scenario: 标记已读

- **WHEN** 专员点击某条反馈通知
- **THEN** 该通知标记为已读，未读计数相应减少

### Requirement: 等待时长可见并触发卡点预警

系统 SHALL 记录每条推荐自提交起的等待工作日数，并在超过阈值时列入"卡点预警"清单；预警项 MUST 支持催办动作且催办留痕。阈值（如 3 个工作日）的口径与是否等同部门反馈时限属 TBD（C4），确认前 MUST 以可配置阈值实现并在界面标注"待确认"。

#### Scenario: 超过阈值仍未反馈

- **WHEN** 某条推荐等待部门反馈超过配置阈值
- **THEN** 该推荐进入卡点预警清单，展示候选人、岗位、已等待天数与提交时间

#### Scenario: 专员催办

- **WHEN** 专员点击"一键催办"
- **THEN** 系统记录催办动作与时间，并向需求提出人发送提醒，催办历史可在留痕中查看
