# Spec Delta

## Purpose

以账号为唯一身份入口、以岗位为数据边界，把"谁能在哪些岗位上做什么"写成可执行的权限契约，确保合规红线（AI 不淘汰、专员不越权）在系统层被强制而非靠自觉。

## ADDED Requirements

### Requirement: 账号状态决定能否登录

系统 MUST 以平台账号作为登录凭证，仅"启用"状态的账号可以登录；"停用"与"待激活"账号 MUST NOT 获得会话。账号被停用后，其会话 MUST 立即失效，且该账号在账号选择与登录入口 MUST 显示为不可登录并给出原因。

#### Scenario: 停用账号尝试登录

- **WHEN** 用户选择或输入已停用账号
- **THEN** 系统拒绝登录并提示"账号已停用，无法登录，请联系平台管理员"

#### Scenario: 会话期间被停用

- **WHEN** 某账号在管理员停用时期仍持有有效会话
- **THEN** 系统在下一次请求时终止会话并要求重新登录

#### Scenario: 待激活账号

- **WHEN** 账号处于待激活状态
- **THEN** 系统拒绝登录并提示需先完成激活

### Requirement: 角色能力矩阵按最小权限强制执行

系统 MUST 按角色校验每项操作：平台管理员可管理用户与平台配置但不参与招聘决策；招聘经理可查看全流程数据、催办与分配专员但不做面试决定与推荐；招聘专员可上传核对简历、提交推荐、发起澄清与催办；用人部门经理可发布岗位、指派本部门面试官、决定是否面试、回评用人结果；用人部门面试官仅可查看材料与回评用人结果。前端隐藏入口 MUST NOT 替代服务端校验。

#### Scenario: 专员尝试做面试决定

- **WHEN** 招聘专员调用同意/拒绝面试接口
- **THEN** 服务端拒绝该请求并返回权限不足，操作未发生

#### Scenario: 管理员尝试提交推荐

- **WHEN** 平台管理员在简历详情尝试提交推荐
- **THEN** 系统拒绝并提示管理员不参与招聘决策

#### Scenario: 面试官尝试发布岗位

- **WHEN** 用人部门面试官尝试发布岗位需求
- **THEN** 系统不提供入口，直接调用亦被拒绝

### Requirement: 岗位维度的数据隔离

招聘专员 MUST 仅能访问自己负责岗位的应聘记录与简历材料；即使同一候选人在其他岗位应聘，专员 MUST NOT 查看那些岗位的材料。越权访问 MUST 被拒绝并记入审计日志。跨岗位的候选人档案仅展示投递岗位名称与对接人，不展示材料内容。

#### Scenario: 专员访问非负责岗位的简历

- **WHEN** 专员通过链接或接口请求非本人负责岗位的简历详情
- **THEN** 系统返回无权限并记录越权尝试（人员、时间、目标资源）

#### Scenario: 候选人多岗投递

- **WHEN** 候选人同时应聘两个岗位，专员仅负责其中一个
- **THEN** 该专员只能看到自己岗位的应聘记录与材料，另一个岗位仅显示存在投递及其对接人

### Requirement: 同岗协作记录可见

同一岗位有多名专员协作时，系统 MUST 向该岗位的协作专员展示已有应聘记录、处理状态与操作人，避免重复录入；该可见性 MUST 以岗位为界，不扩展到其他岗位。

#### Scenario: 同岗重复上传提示

- **WHEN** 专员上传的简历与该岗位已有记录疑似重复
- **THEN** 系统提示已有记录、操作人与时间，由专员确认是否继续

### Requirement: 关键操作留痕且不可篡改

系统 MUST 记录所有关键操作（登录、创建/变更用户与角色、停用账号、发布或变更需求、上传解析、提交/撤回推荐、部门反馈、回评、报表导出）的操作人、时间、对象与结果，日志 MUST 为只读追加且任何角色（含平台管理员）MUST NOT 删除。

#### Scenario: 查询某条记录的操作历史

- **WHEN** 招聘经理或管理员查看一条推荐的全部操作记录
- **THEN** 系统按时间顺序展示每个动作、操作人与结果，且不提供删除入口

#### Scenario: 越权尝试被记录

- **WHEN** 任何角色发起越权操作
- **THEN** 系统在审计日志中记录该尝试及拒绝结果
