# Design

## Context

输入是两份已评审材料：PRD V1.0（业务规则、角色权限、状态流转、C1–C16 待确认项）与一份单文件 HTML 原型（信息架构、页面分区与交互口径已验证，可直接复用文案与布局）。原型只在前端用变量模拟权限与状态，没有服务端、没有持久化、没有真实解析，因此本设计的核心是把"演示正确的交互"转成"服务端无法被绕过的契约"。

约束：飞书仅人工使用，不做系统对接；Offer 流程不在平台内；C1–C16 多数未确认，实现必须可配置而非写死；客户验收包含两条一票否决项（禁止 AI 淘汰、禁止跨岗位越权）。

## Goals / Non-Goals

**Goals:**
- 用一套领域模型承载"需求 → 解析 → 推荐 → 部门反馈 → 回录 → 用人结果"全链路，每一步都有操作人、时间与依据版本。
- 把权限做成服务端强制的能力点 + 资源范围双重校验，前端隐藏仅作为体验优化。
- 让 AI 解析输出可校验、可回溯、且结构上不存在"淘汰"这个动作。
- 让 C1–C16 成为运行时配置与显式 UI 标识，避免口径漂移。

**Non-Goals:**
- 不做飞书排期/消息/单点登录对接（C12 确认前）。
- 不做 Offer 生成、审批、发送。
- 不做小程序端实现（C13 确认前仅保留接口分层，便于后续接入）。
- 不做历史招聘数据迁移与隐私留存策略落地（C15/C16 确认前不预设）。
- 不引入自动淘汰、自动评分调参等任何"机器决策"能力。

## Decisions

### D1 技术栈：React + TypeScript 前端，NestJS + PostgreSQL 后端，对象存储 + 队列

前端沿用原型的信息架构与文案，改用组件库重建（原型中纯 CSS 图表替换为轻量图表库）。后端按模块化单体组织，避免为 6 个业务模块过早拆分微服务。解析任务走队列（上传即入队、失败可重试），PDF 存对象存储，元数据入库。

> **实现记录（2026-10-24）**：受当前运行环境限制（无 PostgreSQL 服务、无前端构建链），实际实现为 **Express + `node:sqlite` + 原生 ESM 前端**。领域模型、能力点矩阵与接口契约与本节一致；`node:sqlite` 与 PostgreSQL 的差异集中在 `server/db.mjs`，迁移到 PG 时只需替换该文件的 SQL 方言与连接层。解析任务当前为同步调用（接口内等待模型返回，前端展示"解析中"），队列与限流列为未完成项（见 tasks.md 4.2b）。

**备选**：直接沿用单文件原型加 localStorage —— 无法满足服务端鉴权与审计要求，仅可作演示；拆微服务 —— 团队规模与需求稳定性不支持。

### D2 领域模型按"需求版本 + 应聘记录"双主键组织

核心实体：`JobRequisition`（岗位需求）、`JobConditionVersion`（条件版本）、`Clarification`（澄清问答）、`ResumeFile`（原始文件）、`Application`（应聘记录＝人×岗位）、`ParsedResult`（解析结论，含逐项结论与证据引用）、`Recommendation`（推荐）、`DeptFeedback`（部门反馈）、`InterviewResult` / `OfferResult` / `Onboarding`、`HiringOutcome`（用人结果）、`User` / `RoleAssignment`、`AuditLog`、`Notification`。

关键取舍：**应聘记录是 Application 而不是 Resume**。同一份简历可对应多条 Application，材料与结论挂在 Application 上，从而天然满足"同人同岗留版本、同人多岗独立保存"（C7 确认前按不覆盖实现）。每条结论保存 `evidence_quote + page + char_range`，保证 R9 的可回溯。

### D3 权限：能力点（capability）× 数据范围（scope）双重校验

定义能力点常量（`job.publish`、`resume.upload`、`recommend.submit`、`feedback.decide`、`outcome.evaluate`、`user.manage`、`report.view` 等），角色到能力点用配置表映射；数据范围由 `RequisitionAssignment`（岗位-专员）与 `dept_id` 决定。守卫顺序：登录态 → 账号状态 → 能力点 → 资源归属。任一失败即拒绝，并写 `AuditLog(action=denied)`。

对 PRD 中标注 `?` 的权限项，默认拒绝（最小权限），配置项保留 `pending_confirmation` 标记，确认后仅改配置不改代码。

角色映射说明：PRD 的四类角色（招聘专员 / 招聘经理 / 用人部门需求提出人 / 客户·人事部门）在实现中细化为五个账号角色，其中"用人部门经理"对应需求提出人的决策权；"用人部门面试官"与"平台管理员"为原型阶段引入的扩展角色（PRD 未显式定义），前者仅可查看材料与回评用人结果、无面试决定权，后者仅治理平台、不参与招聘决策。两者均需在 C11 权限边界确认时一并向客户确认。

**备选**：纯前端路由守卫 —— 不满足 V8"越权访问被拒绝且留痕"。

### D4 AI 解析采用"结构化输出 + 证据校验 + 无决策字段"三重约束

解析服务以"PDF 文本 + 已确认条件版本"为输入，强制 JSON Schema 输出：`score`、`grade`、`tags[]`、`criteria[]`（每条 `verdict: matched|not_matched|insufficient_info`、`evidence_quote`、`evidence_locator`）、`questions[]`。服务端校验：`insufficient_info` 不得映射为 `not_matched`；每条非空结论必须有可定位的原文片段，否则标记 `evidence_missing` 并要求重解析。Schema 中**不存在** `reject/eliminate` 字段，接口层也不提供任何按分数过滤的查询参数。

同时记录 `model_name`、`prompt_version`、`condition_version_id`，用于复盘与问题追溯。

**备选**：让模型直接输出自由文本 —— 无法校验、无法回查证据，违反 R9。

### D5 状态机显式落地，禁止隐式跃迁

需求：进行中 / 挂起 / 结束。应聘记录：解析中 → 待核对 → 待推荐 → 已推荐-待部门决定 → （已反馈-待面试 / 已拒绝 / 待补充）→ 已面试 → 已发 Offer → 已入职。状态变更只允许通过领域服务方法，方法内部校验前置条件（如"提交推荐前必须已确认意向"），并统一写状态流水表。

### D6 通知走 outbox，站内信为主、短信/邮件为辅

部门反馈与用人结果写入 `Notification`（带 `recipient_id`、`read_at`）。订阅关系：反馈 → 推荐专员 + 招聘经理；用人结果 → 推荐专员。外发通过 outbox 表由后台任务投递，避免业务事务里直接调外部服务失败导致数据不一致。

### D7 审计日志 append-only

独立表 + 数据库权限层禁止 UPDATE/DELETE（或使用只追加分区表）。写日志与业务写入在同一事务内完成，保证"操作成功必有留痕"。

### D8 待确认口径用配置中心承载

`SystemConfig` 存 `key / value / status(pending|confirmed) / note`，报表、阈值、权重、评分形态、推送比例均从此读取；前端对 `pending` 项统一渲染"待确认"标签。报表导出接口在相关口径 `pending` 时返回 409 并说明原因。

## Risks / Trade-offs

- [模型幻觉或无证据结论] → Schema 强校验 + 证据定位校验 + 无证据即判 `evidence_missing` 并要求重解析，前端不展示未通过校验的结论。
- [PDF 解析质量参差不齐（扫描件、复杂排版）] → 抽取失败降级为"需人工录入关键信息"，不阻断流程；抽取值与原文对照展示。
- [岗位隔离在聚合查询处漏掉过滤] → 所有数据访问统一走带 scope 的 Repository 封装，禁止裸表查询；补充跨岗位越权用例到自动化测试。
- [口径未确认导致报表被误用] → 看板固定展示"待确认"标识，导出禁用，验收前不提供正式报表。
- [观察期阈值（默认 30 天）与实际试用期不一致] → 作为配置项，回评入口按配置动态开放，界面标注阈值来源。
- [性能：批量上传解析排队] → 队列限流 + 解析状态可见，避免前端超时误判失败。
- [原型与实现漂移] → 以 spec 为验收依据，原型仅作交互参考；文案与分区沿用原型以降低沟通成本。

## Migration Plan

1. 用原型演示数据转成 seed fixtures（岗位、简历、反馈），保证联调阶段页面不空。
2. 按模块灰度上线：先开放"需求 + 解析 + 推荐"，部门反馈上线后同时开启通知；结果回录与看板随数据积累逐步开放。
3. 按 V1 做单岗全流程试跑，通过后再放开多岗位；试跑前采集基线数据（每份简历处理耗时、平均等待），用于对照。
4. 回滚策略：各模块以配置开关控制可见性；解析异常时降级为人工模式，业务不中断。

## Open Questions

- 图表库与组件库的具体选型（不影响接口与规格）。
- LLM 供应商与私有化部署要求（影响成本与合规评估，不改变解析契约）。
