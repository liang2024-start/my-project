1. 项目概述

本系统是一个基于 SSM（Spring + SpringMVC + MyBatis-Plus）+ Vue2 的海鲜自助餐厅管理系统，采用前后端分离架构：

  • 后端：Java WAR 工程，提供 REST 风格 JSON 接口，负责业务逻辑与数据持久化；
  • 前端：Vue2 + Element-UI 单页应用（SPA），已预构建为静态资源（admin/dist），由 Tomcat 一并托管；
  • 业务范围：顾客注册登录、预订餐桌、浏览海鲜菜品、点餐下单、支付结账；管理员对用户、库存、海鲜菜品、餐桌、订单流水进行统一管理。

用户（顾客）yonghu预订餐桌、点餐、查看并支付自己的订单

4. 角色与权限设计

系统采用双账号表设计，而非单表角色字段：管理员存于 users 表（内置 admin/admin）；顾客存于 yonghu 表（可自助注册）。

登录时前端传入 role（管理员/用户），后端校验账号所属表与 role 一致后签发 Token，写入 token 表（有效期 1 小时，过期需重新登录）。前端菜单由 src/utils/menu.js 按 roleName 静态配置：

角色可见菜单可执行操作
管理员用户管理、食物库存管理、海鲜展示管理、未预定餐桌管理、已预定餐桌管理、流水管理各模块增/删/改/查；流水可改
用户海鲜展示管理（点餐）、未预定餐桌管理（预订）、已预定餐桌管理、订单管理查看、点餐、预订、支付

注意：后端接口层面未做细粒度角色校验（仅凭 Token 是否存在），权限控制主要依赖前端菜单收敛。

6. 接口设计

6.1 通用约定

  • Base URL：http://localhost:8080/zizhuchanting/
  • 返回结构（com.utils.R）：{"code":0,"msg":"success",...}；code=0 成功，非 0 失败（401 未登录、500 业务异常、511 数据重复等）。
  • 鉴权：除标注 @IgnoreAuth 的接口外，均需请求头 Token；缺失或过期返回 401"请先登录"。
  • 分页：GET /xxx/page?page=1&limit=10，返回 data.total / data.list。
  • CORS：拦截器统一设置 Access-Control-Allow-* 响应头。

6.2 登录与通用接口

/users/loginPOST免管理员登录（username, password, role="管理员"）
/yonghu/loginPOST免顾客登录（role="用户"）
/yonghu/registerPOST免顾客注册（JSON body）
/yonghu/resetPass—免重置密码

7. 核心业务流程设计

7.1 登录认证流程

前端提交 username/password/role
        │
        ▼
按 role 选表查询（管理员→users，用户→yonghu）
        │  校验 role 与密码（明文比对）
        ▼
TokenService.generateToken：
  生成 32 位随机 token，有效期 1 小时，
  写入 token 表（同人同角色覆盖旧 token）
        │
        ▼
前端保存 token，后续请求统一携带 Header: Token
        │
        ▼
AuthorizationInterceptor：查 token 表且未过期
  → 通过，并把 userId/role 放入 Session

7.2 预订餐桌流程（顾客）

  1. 顾客在「未预定餐桌」列表点击预定；
  2. 后端 /canzhuo/subscribe：餐桌 sf_types=1（已预订），插入 yudingcanzhuo 记录（餐桌 id + 当前用户 id + 时间）；
  3. 一个用户同时只有一条有效预订（点餐时按 yh_types 查询第一条）。

7.3 点餐流程（/haixian/diancai）

顾客在海鲜列表选数量 → 提交 {kuchuen.id: 数量}
        │
        ▼
以当前毫秒时间戳生成订单号 odd
        │
        ▼
逐项校验：海鲜存在 / 数量>0 / 该商品在库存表中存在
          / 用户已预订餐桌 / 购买量 ≤ 库存量
        │
        ▼
写 dingdanxiangqing（订单号、海鲜、单价、数量）
累加流水总价，写 liushui（sf_types=2 未支付，绑定餐桌与用户）
        │
        ▼
扣减 kuchuen 库存，插入流水，返回成功

⚠️ 已知代码缺陷（原项目遗留，重写此模块时须修正）： HaixianController.diancai 中变量 zhi 被赋值为库存记录的主键 id（kuchuenEntity.getId()），却在两处被当作"购买数量"使用：dingdanxiangqing.setNumber(zhi) 与库存扣减 number - zhi。这会导致订单明细的数量、以及库存扣减量都不等于顾客实际购买数量。此外，循环中每次覆盖同一实体再 insert，总价 maxMoney 的累加同样基于错误数量；整个点餐过程无事务回滚保护（事务切面仅覆盖 service 层方法），失败时可能产生脏数据。

7.4 支付/结账流程（/liushui/gaiwei）

顾客/管理员对未支付流水点击支付
        │
        ▼
校验：流水存在 且 sf_types=2（未支付）
        │
        ▼
流水 sf_types → 1（已支付）
餐桌 sf_types → 2（释放为未预订）
删除 yudingcanzhuo 中该餐桌的预订记录

7.5 文件上传流程

/file/upload：按时间戳重命名 → 存入 webapp/upload/ → 返回 http://localhost:8080/zizhuchanting/upload/文件名。注意 WAR 重新部署后 webapp/upload 会被覆盖，上传文件不做持久化。

8. 前端设计

  • 构建产物：src/main/webapp/admin/dist/（index.html + hash 路由），部署后直接随 WAR 访问 /zizhuchanting/admin/dist/；
  • 接口地址：dist/js/index.*.js 中硬编码 http://localhost:8080/zizhuchanting/，若改端口/域名需重新构建（npm run build，Node 建议用 12~14 适配 node-sass）；
  • 主要页面（src/views/）：login（登录/注册，含角色单选）、home（首页轮播+统计）、center（个人信息）、update-password，及 modules 下 yonghu / canzhuo / haixian（含 diancan 点餐页）/ kuchuen / liushui / yudingcanzhuo / dingdanxiangqing / dictionary 各列表页；
  • 状态：登录态（token、角色）存 localStorage / Vuex（src/store）。

10. 设计评价与改进建议

问题风险建议
密码明文存储（users/yonghu）泄露风险改用 BCrypt/MD5+盐
diancai 数量/扣库存 bug（见 7.3）数据错误用"购买数量"替代 zhi，并把点餐包进事务
无物理外键、tinyint 逻辑关联数据不一致建外键或至少加唯一/存在性校验
接口无角色级鉴权越权操作拦截器中按 role 校验写操作
上传文件存 webapp 内重新部署丢失迁移到独立磁盘目录
token 表永不清量缓慢膨胀定时清理过期 token
config 中图片指向旧路径 fd-ssmj图片 404更新 config 表为当前部署地址
